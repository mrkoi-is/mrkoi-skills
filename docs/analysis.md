# 上游分析与 Mr. Koi 个人化说明

分析日期：2026-09-23。上游基线：[4f2db09](https://github.com/KKKKhazix/khazix-skills/tree/4f2db09802736ac8130ddf8dd6121435b5a41b55)。这是一份源码与工作流分析，不是对作者产品效果的全面实测。

## 整体判断

这个仓库的主要价值是把实际工作经验写成可复用的方法。它没有给模型增加训练知识，也不是统一运行的应用：有的 Skill 主要提供提示词和参考资料，有的调用新闻服务，有的携带本地 Python/Bash 脚本。安装成功只说明客户端能发现文件，不证明每个工作流都已经在实际任务中验收。

适合继承的是目标的证据链、横纵研究框架、知识收尾检查和存储报告工具。需要个人化的是作者身份、输出配额、宿主工具假设、任务范围和本地安装更新方式。仅把标题改成 Mr. Koi，会继续得到原作者的口吻与操作习惯。

## 六个 Skill 分析

| 上游 | 核心机制 | 值得保留 | 实际不足 | 个人版 |
|---|---|---|---|---|
| leader | 目标任务书、基线、验收、约束和续跑 | 先看现场事实；防止靠删测试等方式假达标；给并行任务划分责任 | 写死 `/goal` 的字符上限、领导零命令、固定流程；可能把用户指定手段擅自改成另一个目标 | `mrkoi-goal-planner`：明确请求才生成任务书，按宿主能力与用户选择调整结构 |
| neat-freak | 文档、规则、运行态、记忆和残留的事实对齐 | 只读盘点脚本、跨文件核对、场景评测材料；区分代码与实际运行 | 容易因存在远端就进入完整收尾；最初清理授权不被接受；记忆写入边界需服从当前平台 | `mrkoi-project-closeout`：当前项目、当前阶段、直接用户授权，保留已授权操作与未集成工作 |

| aihot | AIHOT 公共 API 查询、热点、日报和增量同步 | 明确端点、空值、时间窗、游标和错误语义 | 依赖外部服务；原更新器下载官方包，会覆盖个人版；聚合摘要不能替代重要事实的一手核对 | `mrkoi-ai-news`：保留 API 路由，增加一手核对，移除原站安装器和 Actor ID 流程 |

这里的“个人化”依据是明确的工作偏好：中文清楚表达、多独立仓库、本地研究与实现优先、保留已有改动、以实际结果验收。没有把私人项目资料、账户内容或个人写作样文导入这个公共仓库。

## 使用上的分工

- **想清楚做什么**：目标规划，产出可执行任务书；普通修复不必先走这一流程。
- **弄清楚为什么与选什么**：横纵研究；新闻 Skill 只负责提供实时线索。
- **把已有材料讲清楚**：个人写作；通用润色仍可继续使用原有 `human-writing`，不替换它。
- **做完后保持资料一致**：项目收尾；不因为 Git 干净就宣称设备、部署或云端状态也已验证。
- **查磁盘占用**：存储分析；生成报告与实际清理是不同操作。

## 改造和维护方式

六个目录均使用独立 `mrkoi-` 名称，并带有 Codex UI 元数据。旧版内容仍可通过 Git 历史追溯，源仓库配置为 `upstream`，个人 fork 配置为 `origin`。同步更新时审阅上游差异，再按目录映射移植，避免把个性化改动覆盖掉。

本地安装器默认预览，确认执行参数 `--apply` 后才建立软链接。遇到已有技能目录或不同软链接时保留原内容并停止；不运行上游远程安装脚本，不维护第二份独立副本。安装器的隔离回归覆盖预览无写入、重复安装、目标冲突、断链保留、失败回滚和目录名校验。

## 后续迭代

写作方面，下一步最有价值的材料是用户自己满意的 3–5 篇文章，以及喜欢和不喜欢的具体段落。研究和目标规划应在真实任务中记录哪里帮上忙、哪里增加了阻力，再针对实际失败精简规则。不要因为有 Skill 就强制给每次任务加一套流程。
