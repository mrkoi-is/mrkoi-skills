# 证据、完成状态与清理

## 结论决定证据

| 结论 | 所需证据 |
|---|---|
| 文档链接有效 | 项目 doc-link/index check，或实际目标存在性 |
| 规则已同源 | readlink/realpath/import 与当前宿主加载机制 |
| 代码实现了某能力 | 当前目标分支实现、配置和针对该能力的检查 |
| 本地功能通过 | 实际操作或测试输出；静态构建不能替代交互 |
| 设备/后端接纳 | 实际安装版本、设备日志和对应后端结果 |
| PR merged | 当前 PR 状态与 merge commit；不能推出部署完成 |
| deployed | 目标环境 release/marker 对应目标版本，并确认服务状态 |
| live verified | 真实用户 URL、API 或设备路径的当前响应 |
| 可清理具体对象 | 用户已有授权覆盖对象，引用和未提交状态已查，无唯一未集成工作或有用户认可的处理方案 |

最终只声明已得到证据的层级。旧 memory、提交信息、页面缓存、终端计划或用户转述可以定位问题，不冒充独立实测。用户陈述可写成「用户确认」，无须为所有文档更新擅自访问生产。

## 事实矩阵

复杂收尾可保留：

```text
topic: 事实主题
scope: 本次仓库、路径和阶段
authority: 当前权威来源
observed: 本次实测 / 用户提供 / 旧记录 / 未验证
action: 修了什么或为何保留
verification: 命令、页面、日志或文件证据
status: verified-current / changed-and-verified / pending / out-of-scope / not-applicable
```

记忆需要额外区分 `generated-read-only`。无需为小改建立固定表格或新文件。

## 阶段分别结束

本地任务可以结束在 `implemented → locally verified → docs aligned`。有 remote 并不要求继续走向发布。

用户明确纳入发布时按真实流程核对 `pushed / PR → merged → deployed → live verified`，各步只证明自己。部署或生产证据缺失则报告所处状态和缺口，不自动执行部署。项目明确规定的发布收尾凭证按适用范围执行；历史流程不能扩展当前授权。

有 CDN、异步进程或多客户端时，只核验本次会影响的表面：origin、新旧缓存、canonical URL、相关 API 和 worker；cache-buster 通常只作诊断。只验证了一部分时写清限制。

## 清理前核验

1. 确定具体对象、归属和用户已有的删除授权。
2. 查固定路径引用、活跃进程和其他使用者；范围不明时保留。
3. 分别查相关仓库、子仓库和 worktree 的 dirty、untracked、detached 与唯一提交；不要只凭「已 merged」或目录名判断。
4. 保留需要交接的证据及唯一资料；先完成必要文档同步。
5. 已有授权具体且满足核验时执行该范围清理。缺的仅是授权时，先提供可审查的候选和理由，再请用户决定；不对相同授权重复确认。
6. 清理后核对仍需保留的工作和实际删除对象，报告残留。

不可把「本地清理安全」统一绑定生产 contains change；只有当前任务属于发布收尾且适用项目规则确有该条件时才核对。规则冲突注明出处，不自行删除规则或忽略当前用户范围。

## 检查失败

重复失败先核查命令、环境和假设，避免盲重试。只回退自己造成的变化；不使用 reset/clean/stash 掩盖失败。缺依赖或权限时交付已完成证据和剩余项，不把未运行检查算通过。
