# 中性改稿示例

以下均为原创假设素材，用来说明编辑方法，不代表 Mr. Koi 或任何人的真实经历。涉及数值时仅在给定假设内成立。

## 把空泛赞美换成可核对结果

假设素材：一批 30 张图片，脚本自动改名 28 张，两张因文件名重复跳过。未记录耗时。

不合适：“这个工具大幅提高了效率，一键解决了全部问题。”

可用：“这批 30 张图片里，28 张完成了自动改名，另外两张因重名被跳过。它已经能处理大部分文件；遇到冲突时怎么决定保留哪张，还需要补一个规则。”

编辑依据：保留成功和失败范围，不补造省时数字。

## 没实测，不补第一人称

假设素材：官方文档写支持 Markdown 导出，用户尚未使用该功能。

不合适：“我用了两周，最喜欢它导出 Markdown 的那一下。”

可用：“文档列出了 Markdown 导出。对已有笔记库的人来说，这值得优先验证：导出的正文、附件和链接能否在现有工具里继续使用。”

编辑依据：把产品声明、判断和建议分开，保留待验证项。

## 不靠口癖制造节奏

原句：“这个东西真的是，怎么说呢，太强了，兄弟们，我直接愣住。”

若假设素材只有“录音能生成带时间点的逐字稿”，可改为：“录音生成逐字稿后，点击一句话就能回到对应时间点。校对时，查找原音频少了一步。”

编辑依据：用具体交互解释价值，不推定作者的情绪。

## 不把推断写成定论

假设素材：某开源工具近期发布了两次修复，修复了用户关注的问题。

不合适：“团队进入高速增长期，已经超越所有竞品。”

可用：“最近两次发布都修复了这个工作流里的问题，说明它仍在积极处理这一场景。能否长期依赖，还要看后续维护与实际使用结果。”

编辑依据：现有证据支持维护动作，不支持增长或行业排名。
