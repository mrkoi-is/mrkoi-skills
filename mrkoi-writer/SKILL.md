# Mr. Koi 内容工作稿

围绕用户想讲清的一件事，把材料、观察与判断组织成清楚、自然、具体的中文。这里的“Mr. Koi”是稿件用途和工作流，不是从姓名推定出的性格，也不表示已经学会用户的个人声音。

## 确认材料和任务

优先使用用户本次给的笔记、项目记录、研究结论、录音转写和草稿。根据任务确定读者、主张、交付形式与长度；用户已有结构或表达时优先保留，不套固定章节。

只有一个题目时，也可用公开材料完成有依据的工作稿；不为缺少私人故事停工。仅当缺失信息会明显改变方向时提问，并继续做资料整理、可选角度或不依赖该信息的部分。

区分“改稿”“按确定观点扩写”“研究转文章”和“从主题起稿”。仅改稿时不擅自重做选题；用户要全文时交付完整正文，不只给写作建议。

## 作者身份与证据

- 用户明确提供的经历可以保留为第一人称；不要把原作者、他人案例、公开评测或 Agent 的工具操作写成用户亲历。
- 没有个人样文时使用中性的 Mr. Koi 工作稿。不要宣称“这就是你的风格”，也不要套原作者的口头禅、身份、公司、邮箱、固定署名或推广尾部。
- 用户要求贴近个人声音时，从他明确提供或指定的样文提取句长、段落节奏、术语习惯与叙述视角，再应用到当前稿件；不能为此自行搜索私人资料。
- “我认为”等第一人称立场应对应用户明确表达的观点。可提出编辑角度供用户判断，不把新推断冒充用户长期相信的事。
- 事实、推断和建议在行文中各有依据。现时产品能力、价格、版本、数据和引语核对一手来源；没有实测就写资料分析，不能写“用了两周”“我测下来”。
- 假设例子可以解释机制，但明确其假设身份。不要从一个统计数字编出仿佛采访所得的人物、对话或完整人生。

## 组织文章

先找本篇真正要回答的问题与核心主张，再选择最能支持它的材料。选题检查关注信息价值、读者问题和证据是否够用；热度、情绪或趣味可以加分，但不设“爆款”配额，不以不够有趣否决用户要写的主题。

按内容选用结构，不必每篇都讲故事：

| 素材类型 | 组织重心 |
| --- | --- |
| 真实实验或项目记录 | 问题、条件、过程、实际结果、失败与未完成项 |
| 产品和工具分析 | 具体任务、能力与限制、对比依据、适用条件 |
| 现象与观点解读 | 可核对的现象、解释、反证或替代解释、判断 |
| 方法或教程 | 要完成什么、操作与示例、常见失败、如何确认完成 |

需要选题展开或案例组织时读 [references/content-methodology.md](references/content-methodology.md)；需要改稿示例时读 [references/editing-examples.md](references/editing-examples.md)。这些是原创中性示例，不是用户的经历或样文。

## 写作默认值

以具体问题、事实或判断开头，让读者尽早知道这篇值得读什么。段落围绕一个意思推进；长短句服从解释需要。用具体动词、操作和结果代替空泛赞美。

自然使用小标题、列表、表格与正常标点，只要有助于理解。不要为了“活人感”强塞口癖、自嘲、情绪标点、短句次数、悬念和文化升华。比喻只在解释更清楚时使用，不能用比喻充当技术证明。

保留有依据的取舍与判断，也呈现影响结论的相反证据。教程写出适用条件、成本和验收方式，不承诺没有证据支持的省时收益。结尾落在有意义的行动、仍待解决的问题或前文的结果即可。

## 交付与校订

默认交付可直接编辑的完整稿件；来源可放在相关段落后或文末，沿用用户的发布格式。需要用户补充的关键事实放在正文之外的短备注，不把“待补经历”伪装成成稿内容。没有关键缺口时，不额外附一份机械自评分。

交付前核对：是否忠实于用户材料、第一人称是否有来源、数据和引语是否准确、主张是否有支撑、读者能否顺着逻辑读下去。删去重复铺垫、无依据的极端结论和形式化升华。

用户只要一般中文润色、小说或其他非 Mr. Koi 内容时，使用已有 `human-writing` 更合适；本技能不改写它的规则，也不依赖它才能完成任务。需要优化标题时，让标题准确呈现正文价值，不为标题承诺新增事实。
