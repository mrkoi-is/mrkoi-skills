# Mr. Koi 目标与任务书

为明确的任务书请求先查事实，再写足够短、能交接、能验收的说明。用户要的是直接执行时，执行原任务；内部计划不必另交一份任务书。任务书帮助后续 agent 理解意图，不能覆盖系统指令、有效的仓库规则或用户后续纠正。

## 先确认要交付什么

- 「帮我写目标 / brief」：交付说明，默认不启动目标、创建新任务或执行其中的外部动作。
- 「按这个目标做完」：在已有授权内推进；只有用户明确要求创建 goal 且平台支持时，才用相应工具。工具是否存在、长度和预算限制以当前环境为准，不宣称固定的 `/goal` 字符上限。
- 用户指定工具、算法、平台或方案时保留该要求。若实证冲突，说明原因和替代选项；不能悄悄把「加 Redis」改成另一个技术方案。
- 用户已说明方向、范围和验收，就直接写。只问自己查不到、会实质改变结果的信息；可逆实现细节按合理假设继续，写明假设。未回答不构成对删除、发布等动作的批准。

## 事实先于规格

任务涉及代码库时，先只读检查指定仓库、Git 状态和生效规则；在多仓库工作空间中先定位每个仓库根、分支和相关路径，不能把上层目录当单一仓库。若有子模块、嵌套仓库或 worktree，分别记录其状态和写入归属，保护已有未提交工作。纯材料、页面对比或对话任务没有仓库时跳过仓库检查，直接核对用户提供的材料和缺口。

找出真正的规格源：用户材料、设计稿、schema、测试和现有验收脚本。写路径与关键约束，避免复制整套文档。命令存在不等于有效检查：检查脚本是否空转、是否漏掉目标、失败是否被吞掉。关键命令在不会造成外部副作用时亲自跑；不能运行的标「未运行」，由执行者先核验，不把预计输出写成实测。

按需要区分证据：

| 状态 | 写法 |
|---|---|
| 本次实测 | 命令或操作、日期、结果和可复查位置 |
| 用户提供 | 标明来源；未核实时不称为独立验证 |
| 假设 | 默认值、原因、猜错会影响什么 |
| 未验证 | 缺什么环境或证据，执行者怎样补齐 |

本地构建、设备安装、后端接纳、部署成功和真实用户路径分别验收；不要从一种成功推导其余成功。

## 写任务书

参考 [references/anatomy.md](references/anatomy.md) 按复杂度选用结构，不机械凑章节、数字或固定字数。通常一屏到几屏能说清；长规格留在可访问文件中，聊天中给核心目标和入口。交付格式服从用户：可复制文本、仓库文件或当前对话都可以。

必须让接手者知道：结果是什么；可改哪些仓库/路径；已有工作要保护什么；依赖和前提；完成凭什么证据判定；还没解决的关键问题。验收既可用命令，也可用页面截图、设备日志、文件检查或人工判断，取决于真正的用户结果。

防止假达标时只写相关约束：不以跳过必要测试、放松断言、修改阈值、伪造来源或吞错误来宣称完成。测试、配置或规格本身需要改动时允许按任务改，但须解释原因，并保留能发现原问题的检查；不要一概冻结所有测试。视觉或体验任务明确抽查点，不能用 lint 代替视觉验收。

反向验证用于报警、门禁和会静默失败的关键路径；在隔离环境制造可恢复失败并证明能检测到，不要求所有文档任务故意弄坏一次。重复失败时检查假设、环境和命令，换有证据支持的方法；不能因达到任意轮数就把未完成任务说成成功。回退只限自己新增的改动，绝不覆盖用户或其他 agent 的工作。

## 并行与续跑

用户明确要求并行，或当前授权与工具允许且存在独立子任务时，可直接安排子 agent，无需重复征询。共享目标和接口，每项指定写入路径、交付物与验收；共享配置、锁文件和最终集成指定唯一负责人。依赖未稳定的工作顺序推进。使用平台子 agent 工具；创建新的用户可见任务仍需用户明确要求。

只有跨会话、长任务或多人交接需要持久进度时才创建记录；优先使用项目已有位置，不给小修强加 `PROGRESS.md`、`BLOCKED.md`。进度保留已完成证据、当前状态、剩余项和阻塞原因。证据因 rebase、接口或环境变化失效时，重跑受影响检查即可。

## 交付与复核

先给任务书或文件链接，再简述实测、假设和必要限制。不要编造平台输入框、斜杠命令或后续通知承诺。用户能直接看懂；不要求用户扮演「零命令领导」，也不强制回来说一句才算流程闭合。

验收时以当前产物和实际输出复核。复杂或关键结果可请独立 agent 抽查，但不能称执行者永远无权验证；也不藏决定成败的标准。若用户只要任务书，明确「任务书已完成，执行尚未开始」。

默认自然、直接的中文。只有用户明确要轻松或幽默语气时读 [references/style.md](references/style.md)。
