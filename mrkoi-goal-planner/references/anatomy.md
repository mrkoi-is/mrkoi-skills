# 任务书的可选结构

按任务复杂度合并或省略章节。以下是内容检查表，不是固定格式或平台限制。

## 目标和背景

用两三句话说明用户想改变什么、完成后的可见结果。区分执行型（交付实现或产物）与探索型（取得可靠答案）；保留用户指定的工具和方案。指明任务书受当前系统、用户和生效项目规则约束，后续纠正优先于旧文本。

## 已确认、假设与待决

把已确认偏好直接落进正文。只有会影响执行的重要假设才单列「问题 → 默认值 → 影响」。需要用户裁量的不可逆、范围外或缺授权动作暂停该部分，继续独立工作；不能写成「无人可问，所以自行批准」。

## 范围和归属

写明仓库根、相关分支/工作树、允许修改的路径以及不能覆盖的现有工作。多仓库分别列范围。指定写入区适合并行；实际发现新增必要文件时按现有授权判断，不以遗漏一条路径为由机械停止。

测试与设计规格是验收依据；只有确实需要保持不变的部分才冻结。需要独立证明无改动时，使用 Git diff 或必要文件哈希。删除、部署、发布、外部发送等按用户已给出的具体授权处理，不从「写任务书」推导执行授权。

## 现状与前提核验

记录会改变决策的实测基线、来源、日期。将未运行的命令列为待核验，不能伪造数字。

关键前提不符时，确认偏差影响哪些任务；更新可复查证据，只暂停依赖该前提的部分。不要把所有轻微基线漂移都升级成整项阻塞。

## 工作项与验收

每项写结果、依赖、范围和可观察验收。检查真实产物，不能用工作量当效果：

- 代码修复：复现原错误，针对修复验证，跑适用的回归检查。
- 网页和应用：实际页面/操作及相应屏幕尺寸或设备；构建通过不能代替可见结果。
- 文档或数据：完整性、事实来源、输出内容与渲染或结构检查。
- 调研：结论、来源日期、未排除的解释和如何复查。负面结果有证据也有价值；不要凑固定结论数。

有意义的负向检查可验证检测器会报警，必须在隔离或可恢复环境中进行。标准变化要说明理由和后果，不隐藏决定成败的检查。

## 交接和完成状态

长任务使用现有进度记录，保存完成证据、待办、阻塞和下一步；短任务可直接在最终回复说明。完成条件围绕用户结果；`已实施 / 本地验证 / 未验证设备或外部系统 / 阻塞` 分开标记。

用户明确提供时间或 token 预算时遵守该预算。预算耗尽、达到重试上限或遇到环境阻塞时如实交付当前结果，不能把「停止」写成「目标达成」。
