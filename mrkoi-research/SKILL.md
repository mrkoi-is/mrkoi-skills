# Mr. Koi 横纵研究

围绕用户正在做的判断：它解决什么问题、怎么走到今天、与可替代方案有何差异、下一步值得验证什么。横纵框架用于补足观察角度，不规定篇幅、章节数或文件格式。

## 确定范围

从用户材料和当前任务中提取研究对象、用途、约束与时间范围。信息足够就开始；只有对象歧义或缺失信息会改变结论时才追问，并继续可独立开展的工作。

默认交付中文研究结论。简要判断可以在对话中完成；复杂任务可保存 Markdown。只在用户需要时制作 PDF。不要因选型问题自动扩展成全面市场、人物生平或发布合规审查。

## 建立证据

- 先读用户提供的材料与指定仓库。涉及当前版本、价格、功能、更新、商业数据、竞争状态时，联网核对一手来源，记录核对日期、版本、地域或套餐条件。
- 技术信息优先官方文档、源码、发布记录、原始论文和原作者说明；不把 arXiv 当作所有学术资料的必经入口。业务数据优先原始公告、公开财报和可解释统计口径。
- 社区讨论用于发现具体体验与问题，保留链接、时间和上下文；不把少数帖子称为用户共识，不把宣传数据称为独立测量结果。
- 搜索摘要只作线索。关键论据尽量读原文；多个转载不算多个独立来源。来源冲突时说明差异，不挑一个有利的数字直接下结论。
- 无法联网或获取全文时，用现有证据完成可做部分，标明过期风险和缺口，不虚构“已查证”。

任务规模足够时，可将时间线、竞品事实、关键论点核验交给独立子任务，使用当前环境实际可用的工具。不要假定某种 Agent、浏览器插件或固定目录存在。

## 使用横纵框架

**纵向：解释今天的来历。** 选择能解释当前定位的节点，例如早期需求、架构选择、关键版本、转型与实际结果。区分当事人公开解释和研究者对动机的推断；时间先后本身不证明因果。历史短的产品可以只保留两三个有意义的节点。

**横向：在同一时间和场景下比较。** 根据用户用途选择代表性对象和指标。写明版本、测试条件、价格口径与比较日期。除直接竞品，也考虑手动处理、既有工具和不采用新方案；没有直接竞品时不强凑名单。列出比较表后解释差异如何影响实际选择。

**交叉：提出可以检验的判断。** 回答哪些历史选择造成今天的优势或限制、哪些对比维度最影响用户、哪些证据可能推翻当前结论。未来情景只有在帮助决策时才写，注明假设、触发条件和可观察信号，不固定编三个剧本。

需要详细问题清单时读 [references/research-framework.md](references/research-framework.md)。需要跨任务交接或机器可读证据时，再读 [references/evidence-record.example.json](references/evidence-record.example.json)，它是示例记录而非 JSON Schema。

## 把证据变成结论

在行文中区分以下内容，不必把每段机械标记为四类：

| 内容 | 写法 |
| --- | --- |
| 事实 | 附支持该主张的来源；测量值写条件、日期和单位。 |
| 推断 | 说明从哪些事实推到什么判断，避免冒充官方解释。 |
| 建议 | 连接用户目标、成本与取舍，给出下一步可验证动作。 |
| 不确定性 | 写明证据缺口、相反证据，以及它会影响哪项结论。 |

开头先给可用结论，再展开支持它的证据。用自然、具体的中文解释机制，保留有信息价值的数字与例子，不为可读性编人物、经历或戏剧冲突。用户明确要中立盘点或自行选择时，给比较依据，不擅自替用户选赢家。

本技能整理研究证据，不模仿原作者的身份或语气。研究稿转成 Mr. Koi 内容稿时可以使用 `mrkoi-writer`；没有该技能也应正常完成研究。

## 可选 PDF

只有需要 PDF 时才使用 [scripts/md_to_pdf.py](scripts/md_to_pdf.py)，具体依赖、命令与验证方法见 [references/pdf-export.md](references/pdf-export.md)。始终保留 Markdown 源文件。生成成功和版面检查是两件事；未经实际渲染检查，不称为“排版已验收”。

## 交付检查

确认核心问题已回答、同一比较口径成立、关键事实能追溯、推断没有伪装成事实；删去不影响结论的重复背景。交付时说明实际查证范围和会改变结论的重要缺口，不附例行的长篇自评。
