# 横纵研究问题清单

这是按需选用的问题清单。用户的决策问题决定保留哪些内容，不要求逐项填写。

## 纵向：发展与路径选择

- 最初要解决什么问题？首个可验证公开版本是什么时候出现的？
- 哪些少数节点改变了架构、用户、分发渠道或收入方式？
- 每次关键选择的已知约束是什么？动机来自公开说明，还是研究者推断？
- 早期选择如何影响兼容性、迁移成本、成本结构与今天的能力？
- 事件发生后有什么可观察结果？有无同期其他因素可以解释结果？
- 哪些信息不足以还原因果？不要用叙事顺畅填补证据空缺。

产品研究重点看版本和实际能力；公司研究重点看业务与组织选择；技术研究重点看原始论文、实现、后续改进和复现条件。人物研究只围绕与问题有关的公开经历与言论。

## 横向：可比较的选择

先定义场景，例如“个人维护的本地工具”“小团队日常协作”，再选择比较对象。

| 维度 | 需要明确的口径 |
| --- | --- |
| 能力 | 版本、套餐、启用条件、功能是宣传还是已验证 |
| 使用成本 | 计价日期、币种、用量、一次性与持续成本 |
| 性能 | 输入、硬件、参数、样本、重复次数与测量人 |
| 集成 | 已有工具、接口、数据格式、迁移与维护工作量 |
| 成熟度 | 发布节奏、可复现问题、文档与维护响应；星标数不等于可靠性 |
| 用户体验 | 具体任务、成功与失败记录、反馈样本的局限 |

只有原始条件可比时才汇总排名。无法实测时明确标为“文档比较”，不要把官方宣称改写成“实测领先”。

## 横纵交叉：可验证的解释

可用以下链条组织判断：历史选择 → 当前可观察差异 → 对用户场景的影响 → 下一步验证。

例如某产品保留本地文件格式，是公开可查的设计选择；能否减少迁移成本仍需用用户的实际文件验证。不要从“本地格式”直接跳到“适合所有人”。

未来推演记录假设和观察信号即可。若历史解释与横向对比相互矛盾，先回查口径和证据，保留仍无法解决的分歧。
